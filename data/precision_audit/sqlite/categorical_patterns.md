# Categorical FP/TP patterns

## MEM31-C

Batch `delta_mem31_task420` (`delta_mem31_b1.json`, 149 findings, sqlite @ b1a73ba34d05). Result: **149 FP / 0 TP**. All findings fell into the following classes — no genuine bug found in this batch.

- **`sqlite3_column_blob()` misattributed as an allocator (46/149 findings, ~31%).** `sqlite3_column_blob()` returns `const void*` (src/vdbeapi.c) — a *borrowed* pointer into the statement's result register, valid only until the next `sqlite3_step`/`reset`/`finalize`/column-type-change. It is never something the caller mallocs or frees. sqc flags the assigned local as an "allocation" and then flags every subsequent return as a leak. Verified across every hit — always read-only use or `memcpy`'d into a real, separately-freed buffer. Examples: `ext/fts3/fts3.c:3006/3031` (`zRoot`), `ext/fts3/fts3_write.c:4313-4884` (`aRoot`/`aHint`), `ext/qrf/qrf.c:1003-1155` (`pBlob`/`a`), `ext/rtree/rtree.c:3944` (`pNode`, immediately memcpy'd into a real `sqlite3_malloc64` buffer at line 3945), `ext/recover/dbdata.c:386` (same memcpy pattern), `ext/session/sqlite3session.c:1390` etc.

- **`int`-returning helper misattributed as a pointer allocator by name (~64/149 findings, ~43%).** sqlite's own `rc`-naming convention (`int rc = someHelper(...)`) collides with sqc's allocator-name heuristic: functions like `sqlite3_initialize`, `sqlite3_wsd_init`, `sqlite3_config`, `sqlite3VdbeList`/`sqlite3VdbeExec`, `statGetPage`, `pager_playback_one_page`, `openDatabase`, `fts3TermSegReaderCursor`, `fts3StringAppend`, `fts3BestSnippet`, `sqlite3Fts5ExprNew`/`sqlite3Fts5ExprAnd`/`sqlite3Fts5ConfigParse`, `fts5ExprPhraseIsMatch`, `closureInsertNode`, `vtshimCopyModule`, `fuzzerRender`, `fuzzParseRecord` — every one is declared to return plain `int` (an `SQLITE_*` status code), verified by reading each declaration. This is the dominant class across `src/main.c`, `src/malloc.c`, `src/os.c`, `src/os_win.c`, `src/pager.c`, `src/vdbeapi.c`, `src/dbstat.c`, `src/complete.c`, and most of `ext/misc/*`. Includes the "may not be freed due to goto" sub-variant (e.g. `src/main.c:3397` etc, `src/dbstat.c:652`, `src/pager.c:2929/2936`, `src/os_win.c:1915`, `ext/repair/checkindex.c:586`) — same root cause, just phrased as a goto-path leak.

- **Static string literal misattributed as heap error message.** `re_compile()` (`ext/misc/regexp.c`) returns `const char*` pointing at a static string literal (`"out of memory"`, `"REGEXP pattern too big"`, or `pRe->zErr` which is itself always set to a literal) — never heap-allocated, never freed anywhere in sqlite, passed straight to `sqlite3_result_error()` which copies it. `ext/misc/regexp.c:788-865`.

- **Ownership-transfer into a struct/list field, freed by the container's own teardown.** Real pointer allocations that are correctly handed off:
  - `sqlite3Fts5Strndup()` results stored into `Fts5Config` fields (`zDb`/`zName`/`zContentRowid`, `ext/fts5/fts5_config.c:589/590/705/717`) or `Fts5ExprTerm` fields (`pTerm->pTerm`/`pTo->pTerm`, `ext/fts5/fts5_expr.c:1789/1798, 2341/2359`) — freed wholesale by `sqlite3Fts5ConfigFree()` / `fts5ExprPhraseFree()`/parse-tree teardown.
  - `zipfileNewEntry()`'s `pNew` (`ext/misc/zipfile.c:1758/1796`) is linked into `pTab`'s entry list via `zipfileAddEntry()` right after allocation.
  - `cidxMalloc()` results (`ext/repair/checkindex.c`): `pRet` stored into `*ppVtab`/`*ppCursor` out-params (freed later by `cidxDisconnect`/`cidxClose`, lines 116/122, 187/190); `azAfter` either freed on the `goto parse_error` path or transferred via `*pazAfter` on success (lines 586/593).

- **Module-persistent field mistaken for an abandoned local.** `pTab->pWriteFd` (`ext/misc/zipfile.c:1522/1538`, real `FILE*` from `sqlite3_fopen`==`fopen`) is a `ZipfileTab` struct field freed by `zipfileCleanupTransaction()` on error and at transaction end on success — not a local.

- **Correctly-scoped resource, freed on every path — sqc over-eager.** `decimalNewFromText()`'s `pX` in `decimalPow2()` (`ext/misc/decimal.c:614`) is freed both at normal loop exit and at the `pow2_fault:` cleanup label.

- **"Stale taint after unconditional free/close" / scope-misattribution.** `ext/misc/fileio.c`: `readFileContents`'s `in` (line 180) is `fclose()`'d immediately before every one of its returns (193, 199) — properly paired. `writefileFunc`'s `out` (line 405) is `fclose()`'d unconditionally right after the write, and the later flagged "leaks" (442-483) are in a *different*, later code block (the `mtime` handling) where `out` isn't even in lexical scope anymore — a straightforward scope-misattribution FP.
